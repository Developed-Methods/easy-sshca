easy-sshca: greenfield implementation plan

Implementation-ready draft · 10 September 2026 · Net-new project with no migration or protocol-compatibility requirements.

Build a small SSH certificate authority with an encrypted SQLite database, a tonic RPC API, and a clap CLI. Each named zone owns one SSH CA. Users request short-lived certificates through named access tokens that belong only to them.

Product scopeArchitectureInitialization and unlockData and permissionsCLI and RPCClient configurationCI trust filesDelivery and verificationAccepted decisions
Committed baseline

One server process uses one local SQLCipher database and two TLS listeners. Tonic serves RPCs, while HTTPS serves public CA files. The server starts locked after every restart. An operator sends the bootstrap secret through RPC to unlock it.

Administration is global, while authorization is explicit. TOTP enrollment and access-token rotation are self-service. Each named access token belongs to one user and has one dedicated API key. Zone permissions and duration limits constrain signing. A web UI, SSO, host certificates, clustering, and a general policy engine are deferred.

2. Process and storage architecture

Use one Cargo package with library and binary targets. Keep protobuf definitions in proto/easysshca/v1. Separate modules for CLI, protocol, server state, storage, authorization, signing, configuration, and public HTTP.

  • RPC: tonic and prost provide versioned protobuf services. Tonic supports TLS through rustls.
  • Database: use rusqlite with bundled SQLCipher. Start with one connection on a dedicated worker and a bounded queue.
  • Concurrency: serialize mutations and signing authorization through that worker. This makes revocation ordering explicit and avoids blocking Tokio threads.
  • Signing: use ssh-key and keep CA private keys in memory only while unlocked. The crate supports certificate generation and signing.
  • Public HTTP: use a small Axum router sharing server state. Separate ports avoid custom HTTP/2 protocol multiplexing.
  • Configuration: use serde with strict schemas. Reject unknown fields, invalid URLs, zero durations, and unreadable TLS files at startup.

Server startup configuration

Keep server configuration at /etc/easy-sshca/server.yaml by default. It contains no database key, admin API key, access-token key, or CA private key.

version: 1
database: /var/lib/easy-sshca/ca.db
rpc_listen: 0.0.0.0:9443
https_listen: 0.0.0.0:9444
tls:
  certificate: /etc/easy-sshca/tls/server.crt
  private_key: /etc/easy-sshca/tls/server.key
limits:
  request_bytes: 65536
  rpc_timeout: 10s
  database_queue: 128

The file uses YAML only and has a required version. Command-line flags may override paths and listener addresses for deployment.

Encryption boundary

Store SSH CA private keys, TOTP secrets, API-key digests, identities, grants, and issuance records inside SQLCipher. Never create a decrypted database copy.

SQLCipher encrypts database pages and journal page data. Temporary storage needs explicit configuration. SQLCipher design reference.

Use memory-backed temporary storage and verify the SQLCipher build at startup. Start with rollback journaling for the single connection. WAL can wait until measured demand justifies it.

Keep only listener settings, database path, and TLS material outside the database. The TLS private key must be accessible before unlock. SSH CA keys remain encrypted.

The unlock key and decrypted data exist in process memory while ready. Disable core dumps and use encrypted swap or disable swap. Zeroize owned secret buffers where supported.

This protects stored CA data and backups. It does not protect a running server from an attacker controlling its process or host.

3. Initialization, locked startup, and recovery

First-time local initialization

  1. Run easy-sshca server init --name "Example SSH CA" --db /var/lib/easy-sshca/ca.db.
  2. Generate a random 32-byte bootstrap secret and an independent random admin API key.
  3. Alternatively, read an operator-provided admin key from --admin-api-key-file.
  4. Create the encrypted database exclusively, then initialize schema version one and the admin-key digest.
  5. Deliver generated credentials once through protected output files or an explicit interactive display.
  6. Store the bootstrap secret separately from the server database and backups.

Initialization is local only. It refuses an existing database and requires no listener. Supplied admin keys must meet the documented random-token format.

Credential output files use exclusive creation and mode 0600. Partial initialization failures must be recoverable without silently replacing credentials or existing state.

Every server start

  1. Load startup configuration and TLS credentials.
  2. Start the tonic listener in LOCKED state.
  3. Expose only unlock, minimal status, and liveness before database access.
  4. Send the bootstrap secret with easy-sshca server unlock --secret-stdin over verified TLS.
  5. Apply the key to a candidate SQLCipher connection before querying.
  6. Read encrypted metadata to validate the key, then check integrity and the exact schema version.
  7. Publish the connection as READY.

A key-setting call alone does not establish successful decryption. SQLCipher requires a database read to verify the key. SQLCipher key API.

The bootstrap secret authorizes unlock. Admin API keys cannot be checked until the encrypted database opens. Unlock returns status only, never an admin credential.

Wrong secrets leave the server locked. Reject concurrent unlock attempts and bound request size, execution time, and retry rate. Once ready, reject further unlock requests.

Use a random secret as the SQLCipher raw key. Human passwords would require a separate password-derivation design and are outside the recommended baseline.

RPC signing and administration return FAILED_PRECONDITION while locked. HTTP trust files return 503. Liveness remains healthy; readiness stays false.

Backup and loss scenarios

The minimal backup procedure stops the server cleanly, then copies the encrypted database. Restart requires another RPC unlock. Never copy only a live database file.

Restore into a stopped instance and unlock with the matching secret. Restore tests must verify CA fingerprints, permissions, and credential state.

Losing the bootstrap secret makes the encrypted data unrecoverable without another valid copy. Database backups alone cannot restore access.

Provide a local offline admin-reset command requiring the bootstrap secret. It replaces a lost admin credential without changing CA keys.

API-key rotation does not change the database encryption key. Database rekeying is a separate offline maintenance feature, deferred from the initial scope.

4. Data model and authorization

TableEssential data
metadataSchema version, immutable instance UUID, display name, and creation time.
zonesUUID, unique name, CA private/public key, fingerprint, maximum duration, next certificate serial, state, and timestamps.
usersUUID, unique username, state, maximum duration, optional confirmed TOTP secret, pending enrollment data, replay state, and timestamps.
access_tokensUUID, owning user UUID, name unique within that user, state, maximum duration, key identifier, secret digest, and lifecycle timestamps.
user_zonesExplicit grants using foreign keys and unique user–zone pairs.
admin_credentialsKey identifier, secret digest, state, and lifecycle timestamps for global administration only.
issued_certificatesZone, serial, user/access-token UUIDs, public-key fingerprint, validity, request UUID, and creation time.
idempotency_recordsActor, operation, request UUID, result digest, status, and expiry for mutation retries.
audit_eventsAdmin and self-service mutations plus signing outcomes, actor IDs, action, result, request UUID, and timestamp. Never store secrets or TOTP codes.

Validate names as nonempty, bounded ASCII letters, digits, underscores, or hyphens. Never turn client-controlled paths into file reads. Apply SQL foreign keys and transactions.

Users represent SSH principals. Each access token is a named credential owned by exactly one user, not an infrastructure host. A user may own several access tokens, but a token cannot act for another user.

Zone access applies to users. Any active access token owned by that user can request the user’s certificate in an authorized zone, subject to the token’s duration limit.

Signing rules

  1. Resolve the active access token from its API secret and load its owning user.
  2. Require an active user, an active token, and the user’s zone grant.
  3. Verify the user’s TOTP policy.
  4. Parse the submitted public key and reject certificates, malformed keys, and unsupported algorithms.
  5. Set the only principal to the owning user’s username; the caller cannot select another user.
  6. Clamp duration to the user, access-token, zone, and requested limits.
  7. Allocate a unique per-zone serial and sign a user certificate in memory.
  8. Commit issuance and TOTP replay state before returning the certificate and expiration.

Accept durations such as 30m, 12h, 1d, and 1w. The default request is 1d. Return the effective duration explicitly.

Set a five-minute validity backdate for clock skew. Enable standard user-certificate extensions for PTY, agent forwarding, port forwarding, X11 forwarding, and user RC.

Use six-digit, zero-padded codes and reject accepted timestep replays transactionally. Enrollment stays pending until confirmation succeeds.

Follow RFC 6238 with SHA-1, 30-second steps, and a ±1-step validation window.

Build the enrollment label as instance_name:username. Put the instance display name in the URI issuer field. Pending enrollments expire after ten minutes.

An authenticated user starts enrollment with any active access token. The server creates a pending secret and returns it once over TLS. The CLI renders the otpauth:// value as a terminal QR code and prints the Base32 secret on its own selectable line, then prompts for a code. Confirmation activates the secret atomically. Cancelled or expired pending enrollments do not affect the current TOTP state.

Self-service may add TOTP but cannot replace or remove confirmed TOTP. If TOTP is already enrolled, a new enrollment request fails. Only an administrator can clear it, after which the user may enroll again.

Credential lifecycle

Each API key contains a public identifier and 32 random secret bytes encoded with unpadded Base64url. Store only a SHA-256 secret digest and compare it in constant time. Each access-token record has exactly one current API key.

Admin creation requires an owning user, a name, and --max-duration, and returns the complete API key once through TLS. Names need only be unique within a user. Listing users or access tokens never returns secret material.

rotate-token is self-service: an active access token authenticates rotation of itself and cannot name another token. The CLI generates and saves the replacement secret securely before submitting it with an idempotency key. The server swaps digests atomically; the previous secret becomes invalid when the transaction commits. A retry with the same idempotency key returns the same outcome without storing retrievable plaintext.

Administrators rotate admin credentials separately. They may revoke or remove a user access token, but do not receive a replacement secret through the user’s self-service path.

A lost access-token creation response is recovered by removing the unusable token and creating another. Do not persist plaintext responses for later retrieval.

Removing a user disables all of that user’s access tokens and removes zone grants. Removing an access token revokes its API secret. Retain stable audit references through tombstones.

Already issued SSH certificates remain usable until expiry. Removal prevents future issuance; it does not terminate SSH sessions. Immediate revocation requires host-side distribution.

5. CLI and RPC surface

Ship one executable with user, administrator, and server subcommands. Command names and output contracts begin at version one.

easy-sshca server init --name "Example SSH CA" --db /var/lib/easy-sshca/ca.db
 easy-sshca server start --config /etc/easy-sshca/server.yaml
 easy-sshca server status
 easy-sshca server unlock --secret-stdin
 easy-sshca server reset-admin --db /var/lib/easy-sshca/ca.db

 easy-sshca admin zone add production --max-duration 1d
 easy-sshca admin zone list
 easy-sshca admin user add alice --max-duration 1d
 easy-sshca admin user list
 easy-sshca admin user remove alice
 easy-sshca admin user grant-zone alice production
 easy-sshca admin user revoke-zone alice production
 easy-sshca admin user totp clear alice
 easy-sshca admin access-token add --user alice --name laptop --max-duration 1d
 easy-sshca admin access-token list --user alice
 easy-sshca admin access-token update --user alice --name laptop --max-duration 1h
 easy-sshca admin access-token remove --user alice --name laptop
 easy-sshca admin key rotate-admin

 easy-sshca configure --server https://ca.example.com:9443 --api-key-stdin
 easy-sshca gen-key --comment alice@laptop
 easy-sshca totp enroll
 # Displays a QR code and selectable Base32 secret, then confirms a TOTP code.
 easy-sshca rotate-token
 easy-sshca pub-key production
 easy-sshca sign production --file ~/.ssh/id_ed25519.pub --duration 1h

Also expose user, access-token, and zone updates for duration limits. Access-token creation requires --max-duration; it has no implicit default.

Global options are --config <path> and --json. Endpoint, trust, credential, zone, key, and duration overrides belong to their relevant commands.

Read API keys and bootstrap secrets through hidden prompts or stdin, never command arguments. Read TOTP interactively by default and support --totp-stdin for automation.

TOTP enrollment intentionally prints the pending secret because manual authenticator setup requires selectable text. Suppress it from debug logs, shell tracing, and JSON error objects.

Separate machine-readable stdout from progress and errors on stderr. Save new local credentials atomically with mode 0600. Never include secrets in Debug output.

For a key named id_ed25519.pub, write id_ed25519-cert.pub. Refuse to replace a certificate unless the user passes --force.

--json emits one versioned JSON object to stdout and no progress text. Use exit code 2 for input, 3 for authentication, 4 for authorization, 5 for unavailable service, and 1 for unexpected failures.

Service: easysshca.v1MethodsAuthorization
BootstrapServiceGetStatus, UnlockMinimal status is public. Unlock requires the bootstrap secret and verified TLS.
AdminServiceCreate/List/UpdateZone; Create/List/Update/RemoveUser; Grant/RevokeZone; Create/List/Update/RemoveAccessToken; ClearTotp; RotateAdminKeyActive global admin API key, ready state.
UserServiceBeginTotpEnrollment; ConfirmTotpEnrollment; RotateTokenActive access token owned by the affected user, ready state. Rotation also requires TOTP when enrolled. Confirmation proves possession of the pending secret.
SigningServiceSignCertificateActive access token, owning user’s zone grant, TOTP policy, ready state.

Send API keys as authorization: Bearer <api-key> metadata. Mark it sensitive. Put TOTP and unlock secrets in protobuf bodies, never URLs.

Return typed TOTP-required details, not string-matched errors. Distinguish invalid input, authentication, authorization, duplicates, unavailable state, and exhausted limits.

Bound messages and list responses. Cap list pages at 100 records and use opaque continuation tokens. Apply a default ten-second client deadline.

Every mutation carries a request UUID and uses a database transaction. Every response and error returns that request UUID for support and audit correlation.

6. Simple client configuration

The client uses YAML only. A single file contains one server connection and one API key. Version one has no profiles, includes, or environment-variable overlays.

Path resolution

  1. Use the path from --config, if provided.
  2. Otherwise, use $XDG_CONFIG_HOME/easy-sshca/config.yaml, if XDG_CONFIG_HOME is set.
  3. Otherwise, use ~/.config/easy-sshca/config.yaml.

Do not search the working directory or system-wide paths. An explicit missing file is an error. A missing default file prints the exact configure command.

Version-one schema

version: 1
server: https://ca.example.com:9443
api_key: "esca_at_EXAMPLE_REDACTED"

# Omit tls_ca to use the operating system trust store.
tls_ca: ~/.config/easy-sshca/company-root-ca.pem

defaults:
  zone: production
  public_key: ~/.ssh/id_ed25519.pub
  duration: 1h
FieldRules
versionRequired integer. Accept only 1. Reject unsupported versions with an upgrade-oriented error.
serverRequired absolute HTTPS URL with an optional port. Reject user information, query strings, fragments, and plaintext HTTP.
api_keyRequired for authenticated commands. It may be absent for pub-key, server status, and initial configuration.
tls_caOptional PEM file. When absent, use operating-system roots. A leading ~/ expands to the user’s home directory.
defaults.zoneOptional zone used when a command omits its positional zone.
defaults.public_keyOptional public-key path. Without it, use unambiguous discovery from standard ~/.ssh paths.
defaults.durationOptional request duration. The built-in value is 1d. Server-side limits always win.

Reject unknown fields and duplicate YAML keys. Resolve relative file paths against the configuration directory. Do not expand arbitrary environment variables or execute substitutions.

Creation, permissions, and updates

configure creates the parent directory with mode 0700 and the file with mode 0600. It prompts before replacing an existing file.

The client rejects configuration files readable by group or other users on Unix. It reports the required chmod 600 correction.

rotate-token writes the complete updated YAML to a mode-0600 temporary file, calls the idempotent rotation RPC, then renames the file atomically.

If the RPC result is uncertain, retry with the same request UUID and candidate key. Never restore the old key after the server confirms rotation.

Command flags override matching configuration values. Configuration values override built-in defaults. Credentials have no command-line override.

Use a separate file through --config for another account or an administrator credential. Profile management is outside version one.

First-user onboarding

  1. Configure an administrator file with the generated admin API key.
  2. Create a zone.
  3. Create the user.
  4. Grant that user access to the zone.
  5. Create a named access token with an explicit maximum duration.
  6. Transfer the one-time API key through an approved secret channel.
  7. Run easy-sshca configure --server https://ca.example.com:9443 --api-key-stdin as that user.
  8. Run easy-sshca totp enroll.
  9. Scan the QR code or copy the displayed secret.
  10. Confirm the generated TOTP code.
  11. Run easy-sshca gen-key.
  12. Run easy-sshca sign production.

The user never selects a username. The server derives it from the configured access token for enrollment, rotation, and signing.

7. HTTP(S) CA files for CI

Serve GET /zones/{name}/ca.pub as an OpenSSH public-key file. This is the only public CA-file route in version one.

“CA files” means public trust material. Private CA keys never leave the server through HTTP or RPC.

Provide HTTPS directly, or loopback HTTP behind an existing TLS proxy. Remote plain HTTP is unsuitable for bootstrapping trusted CA material.

Return a content type, fingerprint-based ETag, and cache revalidation headers. Unknown zones return 404; locked state returns 503.

Serve GET /health/live and GET /health/ready. Liveness returns 200 after listener startup. Readiness returns 200 only while unlocked and ready.

# CI downloads and validates the key before installing it.
curl --fail --show-error --silent \
  https://ca.example.com/zones/production/ca.pub -o ./production-ca.pub
ssh-keygen -lf ./production-ca.pub
# Compare the fingerprint against the expected value held by CI.
# Install atomically after validation.

# sshd_config on hosts belonging to this zone:
TrustedUserCAKeys /etc/ssh/easy-sshca/production-ca.pub

Provisioning must compare the fingerprint, install the file, validate sshd configuration, and reload sshd. Do not replace a working trust file after a failed fetch.

Hosts accept user certificates through TrustedUserCAKeys. Without a principals file, the certificate principal must match the login username. OpenSSH configuration reference.

Each host should trust only its intended zones. Local account creation and shared-account principal mapping remain provisioning responsibilities.

Installed CA keys keep existing hosts independent of CA availability. New provisioning waits for unlock unless public files are mirrored separately.

Cross-cutting implementation requirements

  • Time: use UTC internally and require synchronized server time. TOTP validation and certificate lifetimes depend on accurate clocks.
  • Identifiers: use UUIDv7 values for stored entities and request IDs. Never expose row IDs as protocol identifiers.
  • RPC retries: require request UUIDs for mutations. Cache bounded idempotent outcomes long enough for client retry recovery.
  • Errors: map domain errors to stable gRPC codes and typed details. Human messages may change; machine-readable reason codes may not.
  • Logging: include request UUID, actor type, actor ID, operation, result, and latency. Never log authorization metadata or request bodies containing secrets.
  • Metrics: expose request counts, latency, failure reason, database queue depth, lock state, issuance count, and rate-limit rejections.
  • Rate limits: limit unlock by source address. Limit authentication, signing, TOTP confirmation, and rotation by key identifier and source address.
  • Process isolation: run under an unprivileged account. Restrict database and TLS-key paths through service-manager permissions.
  • Supply chain: pin dependencies, audit advisories and licenses, generate an SBOM, and publish checksums for each release artifact.

Test layers

Unit tests cover duration parsing, configuration validation, token parsing, policy decisions, TOTP windows, and certificate construction.

Database tests cover constraints, transaction rollback, replay prevention, serial allocation, idempotency, and concurrent removal versus signing.

Integration tests start the real server with temporary TLS and SQLCipher files. They exercise every RPC authorization boundary and locked-state response.

End-to-end tests install a CA public key into an isolated sshd, sign a user key, authenticate, and verify expiry behavior.

9. Accepted decisions

These decisions are part of version one. Implementation does not need additional product clarification for them.

Administrator credential

Initialization generates and displays the admin API key once. An operator may instead supply it through a protected file.

The admin API key remains independent from the database unlock secret.

Unlock ownership

An operator invokes the CLI after each restart and sends the bootstrap secret over verified TLS.

Automatic secret-manager retrieval is deferred because it changes the operational trust boundary.

TLS termination

The server terminates tonic TLS and public HTTPS with externally provisioned credentials.

Loopback HTTP behind an existing TLS proxy is permitted. A proxy carrying RPC must support gRPC and protect the backend connection.

User removal and issued certificates

Removal blocks new certificates. Issued certificates remain valid until their natural expiry.

Version one does not publish key-revocation lists or terminate active SSH sessions.

Username meaning

A user name is the local Unix username and the certificate’s only principal. Each access token remains permanently scoped to one user.

Shared-account principal mapping is outside version one.

Public keys while locked

Public CA-file requests return 503 until the server is unlocked. Installed CA keys keep configured hosts independent of CA availability.

Algorithms and release platforms

Version one generates Ed25519 CA and user keys and signs Ed25519 user public keys.

Release artifacts target Linux musl on x86_64 and arm64.

Explicitly deferred

Zone deletion and CA rotation need host trust-change procedures. Database rekeying, online backups, KRL distribution, and overlapping API-key rotation remain separate additions.

Also defer migration tools, compatibility routes, JSON configuration, profiles, SSO, a web UI, host certificates, shared-account principals, clustering, and non-Ed25519 keys.

The first release includes named-zone creation, user and access-token administration, self-service token rotation, self-service TOTP enrollment, admin-only TOTP removal, and user certificate signing.
